Technical learnings · the agent

An agent is a loop that turns words into side effects.

01Each model turn is text or one tool callModelTurn(text=…) · ModelTurn(tool_call=…)

The loop runs the tool, hands the result back, and asks again until there's a reply.

02Tools are where the risk liveslookup_account · issue_refund · close_account

A wrong sentence is embarrassing. A wrong tool call moves money. Review the tools first.

03Cap the loopagent.py · MAX_STEPS = 5

Five model steps per customer message, then a colleague follows up. A runaway loop burns money.

04Swap the model, keep the controlsModel.respond(system_prompt, tools, messages)

One method sits between the agent and any provider. The controls live outside it, so they work with every model.

Technical learnings · Lab 1 · approvals

Classify tools by consequence. Enforce in one place.

01Flag irreversible tools in codetools.py · irreversible=True

The flag sits next to the tool, so neither a prompt edit nor a config release can flip it.

02One choke point for every callagent.py · _guarded_call()

Kill switch, then scope, then approval, then the tool. Same order, on every call.

03Approval is a contractApprover.decide(request) → Decision

A request goes out and a yes or no comes back with a name. A terminal here; a queue or chat button in production.

04Silence means noanswer in ("y", "yes")

Anything else is a refusal: an empty answer, a typo, a closed input. Default deny.

Technical learnings · Lab 2 · scope

Identity comes from the session, never from the chat.

01Bind the conversation when it startsConversation.customer_id

It's set from the sign-in. Nothing the customer types, and nothing the model decides, can change it.

02Check the call's argumentsin_scope(call.args, convo.customer_id)

The tool call has to name the bound customer. A missing id counts as out of scope.

03Refuse before anyone is askedkill switch → scope → approval

An out-of-scope call never reaches an approver, so nobody approves a call that can never be allowed.

04Test what the system did"C-1002" not in lab.db.reads

A reply can hide a leak. The database's read log can't, so the test checks that.

Technical learnings · Lab 3 · traces

Write it down whatever happens, and pin it to what ran.

01One JSON line per steptraces/<run>.jsonl

The customer's message, each tool call and the reply. Any log system can read it.

03Pin each line to the releaserelease · release_hash

The version, plus a hash of the prompt and tool config. That's how you show which release moved the money.

04Traces are personal dataname · email · balance

Who reads them, and for how long, is the data owner's call. Redaction is this lab's homework.

Technical learnings · Lab 5 · injection

Everything the model reads is untrusted input.

01Tool output goes back into the promptlookup_account → nickname → model

Any field a customer can edit is text an attacker can write, and the model reads it as context.

02Put controls on actions, not on text_guarded_call()

A filter on words misses the next phrasing. A check on the tool call holds, whatever the source.

03Show the approver the contextApprovalRequest.customer_said

The action, next to what the customer actually asked. Without it, approvers say yes (ASI09).

04Assume limits are visible"maximum": 100 in the tool schema

The model reads the limit, so an attacker can learn it too (LLM08). Limits catch mistakes, not attackers.

Where controls live

Every control has a part in your code and a part in theirs.

In your code

  • The approval gate
  • The scope check
  • The trace writer
  • A kill switch read on every call

In the cloud account

  • The agent's own identity
  • Trace storage and retention
  • Release history
  • Who may flip the switch

In the customer's systems

  • The approvers, in their tools
  • The sign-in that binds a customer
  • Their audit and log tools
  • The on-call who holds the switch

OWASP's Agent Control Standard (v0.1, September 2026) names this pattern: policy enforcement points at runtime. _guarded_call is one.

0:51. The middle column is the one FDEs forget. kit/controls-map.md has every control across all three columns.
Why not your own AWS account
Run it where the customer can see it, audit it and switch it off.

In your account, their security team can't watch the logs, can't audit a change and can't stop it without calling you. And their data leaves their boundary.
